3. WHY V2 SURVIVES 3,000 CONCURRENT CLIENTS WITHOUT CRASHING

1. Ingestion / Execution Separation:
   The HTTP endpoint does ZERO database lookups or writes. It pushes raw 
   strings to `log_queue` and returns HTTP 202 instantly.

2. Atomic Chunk Reduction:
   Instead of looping single pops, `LMPOP 1 log_queue RIGHT COUNT 500` 
   drains the memory queue in large blocks, reducing context switching.

3. Redis Network Command Bundling:
   Instead of executing 4 sequential async awaits per service, V2 groups:
   `ZADD` + `ZREMRANGEBYSCORE` + `ZCARD` + `EXPIRE` into a single batch. 
   For 5 active services, this translates to 1 network round-trip instead 
   of 20 individual network blocks.

4. Smart Cooldown Suppressor:
   When an error threshold is breached under a 3,000-client load, thousands 
   of parallel alerts could crash the system. V2 targets an atomic distributed 
   lock (`SET NX`). Only 1 thread gets "OK" to invoke the Slack webhook, 
   while the other 2,999 threads drop the alert gracefully while logging 
   efficiently to MongoDB in the background.
